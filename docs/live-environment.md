# Live environment

A real Yocto Wrynose build environment that sous-chef is checked against (M9): the
[bootlin/yocto-kiss](https://github.com/bootlin/yocto-kiss) project, set up with kas and,
separately, with `bitbake-setup`. It lives outside the repository. Nothing in it is ever
built: only parse-only commands and the fetch of one recipe have been run
(live-verification.md).

Everything below was observed on 2026-11-17 on the user's machine (Arch-based; kas reports
"EndeavourOS rolling"; Python 3.14).

BitBake starts on this host: the three host tools it lacked when the environment was first
created were installed afterwards (see [Host tools](#host-tools)). The live verification
(live-verification.md), the differential test (differential.md) and the performance
measurements (performance.md) ran here.

## Create it

```sh
scripts/live-env.sh            # create, or check what is already there
scripts/live-env.sh --verify   # also run the parse-only commands and time them
```

The script needs `python3` (with `venv`), `git` and network access. It:

1. creates `$SOUS_CHEF_LIVE` (default `~/Development/sous-chef-live`);
2. creates a virtual environment `venv/` there and installs `kas==5.5` and
   `bitbake-setup==2.19.0` into it (no `sudo`, nothing system-wide, no shell configuration);
3. clones yocto-kiss (`wrynose`) into `yocto-kiss/` and checks out the pinned commit;
4. writes the kas lock file `yocto-kiss/kas/kiss.lock.yaml` that pins the layers (yocto-kiss
   names branches only, and kas warns "Using branch without commit ... is unsafe"), then runs
   `kas checkout kas/kiss.yaml:kas/dogbonedark.yaml` (never `kas build`);
5. checks the host for the tools in OE-core's `HOSTTOOLS` list and reports the missing ones
   (it installs nothing);
6. sets up the `bitbake-setup` variant in `bitbake-builds/`, reusing the kas clones;
7. prints the paths, versions and commits.

It is safe to re-run: the venv, the clones and both setups are kept, and when every clone
is at its pin and `build/conf/` exists it skips `kas checkout` altogether, so a second run
changes no file. It finishes in under a second (measured: 0.6 s, no network).

If `NETRC_FILE` is set to a file that does not exist, kas refuses to start
(`ERROR - Environment variable "NETRC_FILE" is set, but the path does not exist`); the script
unsets it for its own process. Do the same (`env -u NETRC_FILE ...`) when running kas by hand.

## Where it is

```
$SOUS_CHEF_LIVE/                          ~/Development/sous-chef-live
├── venv/                                 kas, bitbake-setup
├── yocto-kiss/                           the kas project (KAS_WORK_DIR = here)
│   ├── kas/kiss.yaml, kas/dogbonedark.yaml, ...
│   ├── kas/kiss.lock.yaml                written by live-env.sh (not in yocto-kiss)
│   ├── meta-kiss/ meta-kiss-ti/ ...      the project's own layers (in its repository)
│   ├── bitbake/                          cloned by kas
│   ├── openembedded-core/                cloned by kas (layer: meta)
│   ├── meta-arm/                         cloned by kas (layers: meta-arm, meta-arm-toolchain)
│   └── build/                            KAS_BUILD_DIR = BUILDDIR = TOPDIR
│       ├── CACHEDIR.TAG                  kas's marker
│       ├── conf/                         bblayers.conf, local.conf (generated by kas)
│       ├── downloads/ sstate-cache/ cache/
│       └── tmp/                          TMPDIR (work/ holds curl's and the scratch fetch)
├── bitbake-builds/                       the bitbake-setup "top directory"
│   ├── site.conf                         DL_DIR, SSTATE_DIR for all setups below
│   ├── .bitbake-setup-downloads/         DL_DIR (git mirrors of the fetched layers)
│   ├── .bitbake-setup-cache/
│   └── kiss-wrynose-dogbonedark/         the setup directory
│       ├── config/                       config-upstream.json (a git repository)
│       ├── layers/                       bitbake, openembedded-core, meta-arm, meta-kiss are
│       │                                 symlinks into yocto-kiss/; meta-yocto,
│       │                                 meta-openembedded, meta-xilinx are fetched
│       └── build/                        BUILDDIR, with init-build-env and conf/
├── bitbake-setup-sources.json            bitbake-setup --source-overrides (pins + local links)
├── scratch/                              left by the live verification (see below)
└── runs/                                 raw output: the script's runs, --verify, verify/,
                                          differential/, perf/, the fix rounds, docs/
```

kas clones every repository into its work directory, which is the directory it is started
from: here `yocto-kiss/`, next to the kas files. `meta-kiss` and `meta-kiss-ti` have no `url`
in the kas files; kas logs "Using .../yocto-kiss as root for repository meta-kiss". For
`dogbonedark` kas clones only `bitbake`, `openembedded-core` and `meta-arm`; the README's
`meta-openembedded` and `meta-xilinx` are only for the `krazymp` board. The clones are full
(not shallow).

## Point tests at it

Set `SOUS_CHEF_LIVE` to the directory. The live tests are `#[ignore]`: `tests/live_verify.rs`
(live-verification.md), `tests/kas_live.rs` (kas discovery against `bitbake-layers
show-layers`), `tests/differential.rs` (differential.md) and `tests/performance.rs`
(performance.md). All but `kas_live.rs` return at once without `SOUS_CHEF_LIVE`. Two start
BitBake, parse-only: `kas_live.rs` runs `bitbake-layers show-layers` through kas, and
`differential.rs` runs `scripts/differential.sh` for a missing dump.

```sh
SOUS_CHEF_LIVE=~/Development/sous-chef-live cargo test --test live_verify -- --ignored
```

From there: the kas project is `$SOUS_CHEF_LIVE/yocto-kiss` with the files
`kas/kiss.yaml:kas/dogbonedark.yaml`; its build directory is `$SOUS_CHEF_LIVE/yocto-kiss/build`;
kas is `$SOUS_CHEF_LIVE/venv/bin/kas`; the `bitbake-setup` build is
`$SOUS_CHEF_LIVE/bitbake-builds/kiss-wrynose-dogbonedark/build`.

A parse-only command through kas:

```sh
cd $SOUS_CHEF_LIVE/yocto-kiss
env -u NETRC_FILE ../venv/bin/kas shell kas/kiss.yaml:kas/dogbonedark.yaml -c 'bitbake -e curl'
```

## Delete it

```sh
rm -rf ~/Development/sous-chef-live
```

Nothing else on the machine is touched by the script or by the commands in this document:
kas runs `bitbake` with `HOME` set to a temporary directory, and `bitbake-setup` was given its
top directory on the command line, so no `~/.config/bitbake-setup/settings.conf` is written.

## What it costs

| | Time | Disk | Network |
|---|---|---|---|
| venv + kas + bitbake-setup | ~4 s | 30 MB | PyPI |
| yocto-kiss clone | ~1 s | (in the line below) | GitHub |
| `kas checkout` (bitbake, openembedded-core, meta-arm) | ~10 s | 284 MB for `yocto-kiss/` | git.openembedded.org, git.yoctoproject.org |
| `bitbake-setup init` (meta-yocto, meta-openembedded, meta-xilinx) | ~8 s | 174 MB for `bitbake-builds/` (126 MB of it DL_DIR) | git.yoctoproject.org, git.openembedded.org, GitHub |
| **whole script, from nothing** | **~31 s** | **487 MB** | about 420 MB |
| second run | 0.6 s | 0 | none |

Measured on a fast connection (30-60 MiB/s). Once the host tools were installed, BitBake
parsed the 1033 recipes of the kas build (`Parsing of 1033 .bb files complete (0 cached,
1033 parsed)`); a `bitbake -e curl` with a warm cache takes about 3 s, about 5 s per recipe in
the differential script.

**Side effects seen in the verification.** `bitbake -n -c fetch curl` (a dry run) is not
network-free: it downloaded the uninative shim (`build/downloads/uninative/`, 7 MB) before
BitBake disabled uninative for the newer host glibc. A deliberately broken fetch (a scratch
recipe with an `.invalid` URL) did not stop at the DNS failure: OE-core's `MIRRORS` made wget
ask `downloads.yoctoproject.org` and `mirrors.edge.kernel.org` for the file. A scratch recipe
meant to contact nothing must set `MIRRORS = ""` and `PREMIRRORS = ""`. sous-chef writes its
index and handles under `$XDG_CACHE_HOME/sous-chef/` (default `~/.cache`): set
`XDG_CACHE_HOME` to a directory under `runs/` when experimenting, so nothing lands in the
user's cache.

## Limits

What may be run in this environment is fixed by the user's rule in
[M9, "Limits on live runs (binding)"](milestones/M9-kas-live.md#limits-on-live-runs-binding):
parse-only commands (`bitbake -p`, `bitbake -e`, `bitbake-getvar`, `bitbake-layers show-*`,
`kas dump`, `kas shell -c` running one of these), and `-c fetch` / `-c unpack` / `-c patch` of
one small recipe. Nothing that compiles, no image, no `kas build`, no `bitbake kiss-image`.
`do_unpack` and `do_patch` may need native tools built first; check with `bitbake -n` before
running them.

## Host tools

When the environment was created, BitBake's first check (`base.bbclass`, on
`ConfigParsed`) failed on this host:

```
ERROR: The following required tools (as specified by HOSTTOOLS) appear to be unavailable in PATH, please install them in order to proceed:
  chrpath diffstat rpcgen
```

(printed twice by `bitbake-layers`). Every other tool in OE-core's `HOSTTOOLS` list was
present. On Arch the packages are `chrpath`, `diffstat` and `rpcsvc-proto` (for `rpcgen`);
the user installed them afterwards, and BitBake has started since. Before that, `bitbake
-p`, `bitbake -e`, `bitbake-layers show-*` exited 1 after about 1.5 s with the message above,
and `bitbake-getvar` exited 1 with the same message followed by a Python traceback
(`bb.tinfoil.TinfoilUIException`, then `bb.BBHandledException`). The samples under
`tests/fixtures/outputs/live/` that show this failure are from that time (its README says
which). `scripts/live-env.sh --verify` finishes the `bitbake-setup` build (see below) and
times each parse-only command.

## What kas produced

**Build directory.** `KAS_WORK_DIR` defaults to the current directory and `KAS_BUILD_DIR` to
`<work dir>/build` (`kas/context.py`); here `yocto-kiss/build`. `TOPDIR`, `BUILDDIR` and
`BBPATH` are that directory.

**`TMPDIR` is `build/tmp`, not `build/tmp-glibc`** as the yocto-kiss README says. OE-core
Wrynose has `TMPDIR ?= "${TOPDIR}/tmp"` (`meta/conf/bitbake.conf:405`) and marks
`TCLIBCAPPEND` as renamed ("is no longer used, modify TMPDIR directly if required",
`bitbake.conf:109`); neither yocto-kiss's distro nor kas sets `TMPDIR`; and BitBake's first
run created `build/tmp/hosttools/`. Confirmed since: `bitbake-getvar --value TMPDIR` prints
`<work dir>/build/tmp`, as does `build/tmp/saved_tmpdir`.

**Markers.** kas wrote `build/CACHEDIR.TAG`:

```
Signature: 8a477f597d28d172789f06886806bc55
# This file is a cache directory tag created by kas.
# For information about cache directory tags, see:
# https://bford.info/cachedir/spec.html
#
# kas build directory
```

kas did **not** write a `.config.yaml`: that file (`CONFIG_YAML_FILE` in `kas/config.py`)
is written only by `kas menu`, and is read as the default configuration when no file is given.
Nothing else in the tree names the kas files that were used; `.kas_shell_history` would
appear in `yocto-kiss/` after an interactive `kas shell`.

**`build/conf/bblayers.conf`** (no "generated by kas" comment; the paths are relative to
`${TOPDIR}`, sorted by path):

```
BBLAYERS ?= " \
    ${TOPDIR}/../meta-arm/meta-arm \
    ${TOPDIR}/../meta-arm/meta-arm-toolchain \
    ${TOPDIR}/../meta-kiss \
    ${TOPDIR}/../meta-kiss-ti \
    ${TOPDIR}/../openembedded-core/meta"
BBPATH ?= "${TOPDIR}"
BBFILES ??= ""
```

**`build/conf/local.conf`** (again no generated-file marker; kas writes each
`local_conf_header` entry under a `# <key>` comment, then `MACHINE`, `DISTRO` and
`BBMULTICONFIG`):

```
# meta-kiss
# Some useful lines you may want to copy to your local.conf for development
# INHERIT += "rm_work"
# OE_FRAGMENTS += 'core/yocto/root-login-with-empty-password'

MACHINE ??= "dogbonedark"
DISTRO ??= "kiss"
BBMULTICONFIG ?= ""
```

So kas does **not** mark the files as generated. It rewrites both on every `kas checkout`,
`kas shell` and `kas build`: all three run the same setup steps (`Macro` in
`kas/libcmds.py`: repos checkout, patches, `SetupEnviron`, then `WriteBBConfig`, which opens
both files with `'w'`), so an edit made there is lost on the next kas run, and every
`kas shell -c` re-checks the repositories first (about 0.4 s here, no network when the
pinned commits are present). A rule that wants to recognise a kas build directory must use
`CACHEDIR.TAG` ("kas build directory"), the kas files next to it, or `sous-chef.toml`, not a
header in the `.conf` files. The other files in `build/conf/` (`conf-notes.txt`,
`conf-summary.txt`, `templateconf.cfg` = `meta/conf/templates/default`) come from OE-core's
`oe-setup-builddir`: kas sources `oe-init-build-env` (`get_build_environ` in
`kas/libkas.py`) to capture the build environment, and that creates them.

**`kas dump`** prints the merged configuration with the lock file's `overrides:` first (see
`tests/fixtures/outputs/live/kas-dump.yaml`); `kas dump --lock` prints only the lock.

**Environment inside `kas shell`** (`kas shell <files> -c 'env | sort'`, recorded in
`tests/fixtures/outputs/live/kas-shell-env.txt`). kas starts from an empty environment:

- `BUILDDIR` and `BBPATH` = `<work dir>/build`; the command runs with `PWD` = the build
  directory.
- `PATH` = `openembedded-core/scripts:bitbake/bin:/usr/sbin:/usr/bin:/sbin:/bin` (the user's
  `PATH` is **not** kept); `OE_ADDED_PATHS` the same two directories; `PYTHONPATH` =
  `bitbake/lib:`.
- `HOME` is a **temporary directory** (`/tmp/tmpXXXXXXXX`), not the user's home.
- `BB_ENV_PASSTHROUGH_ADDITIONS` = OE-core's list plus `SSTATE_DIR SSTATE_MIRRORS
  BB_HASHSERVE_DB_DIR BB_HASHSERVE BB_HASHSERVE_UPSTREAM DL_DIR TMPDIR`.
- `LANG`/`LC_ALL` = `en_US.UTF-8`, `LANGUAGE=en_US:en`, `NO_COLOR=1`, `GIT_TERMINAL_PROMPT=true`,
  `HISTFILE=<work dir>/.kas_shell_history`, `SHELL`, `TERM`, `LOGNAME`, `SSH_AUTH_SOCK`.
- **`KAS_BUILD_DIR`, `KAS_WORK_DIR` and every other `KAS_*` variable are not set** inside
  the shell. They are inputs kas reads (`kas/context.py`), not something it exports. Detection
  of a kas project from inside `kas shell` cannot rely on them.
- The `-c` command is run with the user's login shell: kas logs
  `Command "/usr/bin/zsh -c 'bitbake -p'"` here. Quoting in the command string must therefore
  be valid for whatever `$SHELL` is, not only for `sh`.
- kas prints its own log lines (`2026-11-17 16:19:03 - INFO     - ...`) on stderr before and
  after the command, ending with `To start the default build, run: bitbake -c build
  kiss-image`; on failure it adds `ERROR    - Shell returned non-zero exit status` and
  `ERROR    - Command "..." failed with error 1`, and exits 1.

## The `bitbake-setup` variant

`bitbake-setup` is installed from PyPI into the same venv. Run non-interactively (flags from
`bitbake-setup --help` and `bitbake-setup init --help`):

```sh
cd $SOUS_CHEF_LIVE
venv/bin/bitbake-setup --setting default top-dir-prefix $SOUS_CHEF_LIVE \
    --setting default top-dir-name bitbake-builds \
    init --non-interactive --source-overrides bitbake-setup-sources.json \
    yocto-kiss/yocto-kiss.conf.json dogbonedark
```

- `--non-interactive` suppresses all three prompts ("Proceed?" for a new top directory,
  "Enter setup directory name", "Continue?"). The configuration name (`dogbonedark`) after
  the config file selects the sub-configuration; without it, per `--help`, a
  non-interactive run "will stop with a failure" (not tried).
- The config is the local `yocto-kiss.conf.json` at the pinned commit rather than the README's
  `https://raw.githubusercontent.com/.../refs/heads/wrynose/yocto-kiss.conf.json` (the same
  file today, but the URL follows the branch).
- `--setting default top-dir-prefix|top-dir-name` (for this invocation only) keep it in the
  live directory; the defaults are the current directory and `bitbake-builds`, and the global
  settings file `~/.config/bitbake-setup/settings.conf` is only read, never written by `init`.
- **It reused the kas layers.** `-L <source> <path>` (`--use-local-source`), or a `local` entry
  in a `--source-overrides` JSON file, makes `layers/<source>` a symlink to an existing
  checkout. bitbake, openembedded-core, meta-arm and meta-kiss (= the yocto-kiss clone) are
  symlinks into `yocto-kiss/`; `init-build-env` resolves them, so the build uses
  `yocto-kiss/openembedded-core/oe-init-build-env` and `yocto-kiss/bitbake/bin`. The
  configuration lists seven sources and bitbake-setup fetches every one, whichever machine is
  chosen, so meta-yocto, meta-openembedded and meta-xilinx were downloaded (126 MB of git
  mirrors in DL_DIR, about 48 MB checked out); the overrides file pins them to commits.
- **The setup directory is `bitbake-builds/kiss-wrynose-dogbonedark`, not
  `bitbake-builds/kiss-wrynose`** as the README says: bitbake-setup appends the
  sub-configuration's `setup-dir-name` (`-dogbonedark`) to the parent's (`kiss-wrynose`).
- `init` **failed at its last step** (exit 1) the first time: after writing the build
  directory it runs `bash -c '. <build>/init-build-env && bitbake-config-build
  enable-fragment distro/kiss machine/dogbonedark'`, which started BitBake and hit the
  HOSTTOOLS error. A second `init` would only say "Setup already initialised";
  `scripts/live-env.sh` ran the `enable-fragment` step itself once the host tools were
  present, so `conf/toolcfg.conf` now holds `OE_FRAGMENTS += "distro/kiss
  machine/dogbonedark"`, which is where this build's `MACHINE` and `DISTRO` come from. (OE-core's
  `meta/lib/bbconfigbuild/configfragments.py` writes fragments to `conf/toolcfg.conf`, which
  `bitbake.conf` includes after `conf/auto.conf`.)

**`init-build-env`** is at `<setup dir>/build/init-build-env`
(`bitbake-builds/kiss-wrynose-dogbonedark/build/init-build-env`). It is a wrapper meant to be
sourced, and takes **no arguments** (it overwrites the positional parameters):

```sh
# init-build-env wrapper created by bitbake-setup
cd {{LIVE}}/yocto-kiss/openembedded-core
set {{LIVE}}/bitbake-builds/kiss-wrynose-dogbonedark/build
. ./oe-init-build-env
set --
```

That is, it is `. oe-init-build-env <build dir>` from the OE-core directory, so
`oe-init-build-env` still works for such a build. (If the configuration had
`bb-env-passthrough-additions`, bitbake-setup would prepend an `export
BB_ENV_PASSTHROUGH_ADDITIONS=...` block; yocto-kiss has none.) Sourced in
`env -i PATH=/usr/bin:/bin bash`, it sets `BUILDDIR` and `BBPATH` (= the build directory),
`BB_ENV_PASSTHROUGH_ADDITIONS` (OE-core's list), `OE_ADDED_PATHS`, prepends
`openembedded-core/scripts:bitbake/bin` to `PATH`, sets `PYTHONPATH=bitbake/lib:`, and leaves
the shell in the build directory; it prints `conf-summary.txt` ("A fictitious product which in
reality implements the BeagleBone Black"). No `KAS_*` and no bitbake-setup-specific variable.
bitbake-setup itself recognises a setup by `BBPATH`'s first entry containing `init-build-env`.

**Build directory and `conf/`**: `<setup dir>/build` and `<setup dir>/build/conf`.
bitbake-setup writes `conf/` itself (not from an OE template): `bblayers.conf` with absolute
paths through the `layers/` symlinks and no `BBPATH`/`BBFILES` lines; a `local.conf` that is
only a comment; empty `conf-notes.txt` and `templateconf.cfg`; `conf-summary.txt`; and
`site.conf`, a symlink to the top directory's `site.conf` (which sets `DL_DIR`,
`SSTATE_DIR = bitbake-builds/.sstate-cache` and `BB_HASHSERVE_DB_DIR`). It writes no
`auto.conf`. The layer list differs from kas's: it adds `meta-yocto/meta-poky` and
`meta-yocto/meta-yocto-bsp`. A setup also has `config/config-upstream.json` (the
configuration and overrides used, in a git repository) and `layers/.oe-layers.json` (every
layer found under `layers/`).

**`bitbake -p` from it** failed the same way before the host tools were installed
(HOSTTOOLS, exit 1, 1.0 s); it parses now.

The recorded files are in `tests/fixtures/outputs/live/` (see its `README.md`).

## What the verification left

`scratch/` (all of it from the live verification): `sous-chef*.toml` configurations, the
`cache/` it used as `XDG_CACHE_HOME`, the scratch layer `meta-scratch/` (with the broken
fetch recipe), `kas-scratch.yaml`, `wrapper-test/` and helper scripts (`mcp.py`, `sc`,
`kasrun`, `lintsum.py`, ...). In the kas build, the fetches left `build/downloads/` and
`build/tmp/work/.../curl/` and `.../broken-fetch/`. `runs/` holds raw outputs. To remove
what the verification added: `rm -r scratch runs/verify` in `$SOUS_CHEF_LIVE`, and, if
wanted, `yocto-kiss/build/downloads` and `yocto-kiss/build/tmp/work` (BitBake recreates
them). Deleting the whole directory (above) removes everything.
